# 多设备架构检查与改进

2026-09-07。目标：手机能迅速看懂每台电脑上的 Codex 任务，并向确定的会话可靠发送 Prompt。

本文保留早期直连架构检查及后续事件同步改造记录。当前推荐 NAS / 常开主机 Hub 汇聚方式；完整拓扑、部署与更新步骤以 [README](../README.md) 为准。下方测试数量属于各阶段记录。

## 检查结论

| 原实现的问题 | 对使用的影响 | 本次处理 |
| --- | --- | --- |
| 手机只保存一个 `SavedDevice` | 必须切换入口，不能统一了解多台电脑 | 增加设备注册表和统一工作台，自动迁移原有连接 |
| 会话哈希是手机本地状态的唯一键 | 复制过的会话可能跨设备共享草稿或隐藏状态 | 本地键包含 Relay、手机注册 ID 和会话哈希；网络请求保留原始哈希 |
| 每次刷新并行读取四个接口 | 多机请求数增加，状态与回执可能来自不同瞬间 | 新增鉴权 `/snapshot`，一次返回状态、会话、事件、回执；兼容旧 Relay |
| 状态依赖生命周期 Hook | 漏掉结束事件后可能一直显示工作中 | 叠加 App Server 的新鲜运行状态；无运行证据标记为上次状态 |
| 会话与 Prompt 共用 24 小时清理 | 长时间运行或等待决定的任务可能消失 | Prompt 仍按 24 小时删除；运行、待决定、失败、中断会话保留，容量提高到 128 |
| 手机每次尝试都生成新的幂等键 | HTTP 回应丢失后手动重试可能重复运行 | 同一页面生命周期内，相同目标和内容的未确认重试复用请求 ID |
| Queue 与 Steer 共用等待链 | Steer 被等待当前回合结束的 Queue 挡住 | 按桌面会话和输入模式隔离队列；同一会话跨手机 Queue 串行 |
| 超时统一算失败；成功回执超过 TTL 算过期 | 用户可能重复发送已经执行的指令 | 增加 `unknown`；确认成功的晚回执仍是 `sent` |
| 一个 Service Worker 订阅承载所有电脑 | 不同 VAPID 密钥互相替换订阅 | 每台电脑独立推送 scope，通知包含不透明设备引用 |

## 早期直连拓扑（仍可选用）

```text
手机上的一个 Codexy PWA
  ├─ 设备 A 凭据 → 私有 HTTPS → Relay A → loopback App Server A → 多条 Codex 会话
  ├─ 设备 B 凭据 → 私有 HTTPS → Relay B → loopback App Server B → 多条 Codex 会话
  └─ 设备 C 凭据 → 私有 HTTPS → Relay C → loopback App Server C → 多条 Codex 会话
```

直连适用于单用户、少量设备场景；需要固定手机入口和常开状态汇聚时使用 Hub。
不同电脑的读取独立完成：一台超时不会阻塞其他设备；每台最多一个汇总读取在途。
后台暂停事件连接，返回前台立即重新同步。离线保留当前页面内的旧快照，但不把旧状态当成正在运行的事实。

工作台把设备管理折叠，优先展示需要决定、失败、中断、结果待复核的任务。每条卡片分别说明
Agent 的进展和用户下一步。点开会话后才提取回复速览，完整回复不会进入聚合接口。

## 模块边界

- `src/FleetApp.tsx`：设备增删、统一工作台、目标会话导航。
- `src/fleet.ts`：设备与会话作用域、状态新鲜度、独立快照读取和排序；不持有全局默认发送目标。
- `src/liveSync.ts` 与 `relay/change-feed.mjs`：鉴权长轮询、变化通知、后台暂停与断线重连。
- `App.tsx`：复用已有单设备控制页面，以明确的 `initialDevice` 注入目标。
- `src/promptDelivery.ts`：HTTP 未确认重试和同次点击去重。
- `relay/session-projection.mjs`：生命周期状态与运行时证据的公开投影，不读取对话。
- `relay/remote-commands.mjs`：内存命令、幂等校验、队列、过期和回执。
- `relay/codex-control.mjs`：本机 Codex 协议适配，保留 loopback 约束。

`idle` 表示当前无运行回合，不能推断整个目标完成。运行状态与 Steer 的 active-turn 前置条件按
[Codex App Server 官方文档](https://learn.chatgpt.com/docs/app-server) 核对。

## 多设备接入

1. 每台电脑安装 Codexy，运行各自的 Relay 和 Codex 控制桥接。
2. 手机固定打开其中一个私有 HTTPS 工作台地址，并添加到主屏幕。
3. 在其他电脑的 `.env.local` 中，将 `CODEXY_ALLOWED_ORIGINS` 设为该工作台的**完整 origin**，例如
   `https://my-workbench.example.ts.net`，然后重启那台电脑的 Relay。多个明确授权地址用逗号分隔；不使用通配符。
4. 在手机设置中点击“添加电脑”，填写别名和目标电脑的私有 HTTPS 地址，在目标电脑执行显示的 `codexy pair 六位码`。
5. 在各电脑的项目目录运行 `codexy`。全部设备的任务会汇总到同一页。
6. 各电脑的后台通知在“管理设备 → 控制与通知”中分别启用；无需复制 VAPID 私钥。

已有连接会自动迁移。迁移不改变 Relay 凭据或其他设备的配对。
普通 `codex` 进程的 Hook 可提供观察信息；远程输入需要支持直接输入的会话，通常应通过 `codexy`
启动或恢复。无法承诺无缝接管所有已经运行的独立 CLI。

## 投递语义与限制

- `queued/waiting`：尚未送达，可撤回；`dispatching`：已开始投递，不能保证撤回。
- `sent`：Codex 已确认接收；**不表示工作完成**。
- `unknown`：投递时连接中断，可能已接收；查看会话后再决定，系统不自动重放。
- 完整远程 Prompt 只存于本机内存队列，终态及等待过期后删除；手机草稿按设备和会话隔离。
- 幂等记录只在 Relay 内存中保留一小时；手机未确认尝试保留 30 分钟。页面重载、Relay 重启或保留期外，
  不提供 exactly-once 保证。重启后不会自动重放旧指令。
- 统一工作台只缓存页面内快照；首次打开时离线电脑无法提供历史详情。
- 工作台 PWA 的首次载入仍依赖提供静态文件的那台电脑。已安装并缓存的 shell 可离线启动，但这不是独立高可用服务。
- 当前概览采用事件失效通知加完整快照校验；重连读取最新快照，不提供历史事件日志断点回放。
- `needs_you` 提醒和上下文可以远程查看；授权操作仍由电脑端处理，Codexy 不自动批准。

## 后续架构演进

App Server 生命周期通知与低频校验已接入。新增 `hub/` 实现飞牛 NAS 私有中枢：电脑主动建立鉴权 WebSocket，手机经单一 HTTPS 入口读取脱敏快照和定向提交指令。
中枢只在内存保留最新脱敏快照和等待回执的请求标识；磁盘只保存设备注册和凭据哈希。重启后等待电脑重连，不重放指令。
原始工作目录、thread ID 和完整 Prompt 不进入中枢持久状态。指令排队、去重、Steer 校验仍由目标电脑执行；中枢断线拒收新指令，已投递但未获回执明确标记未知。
锁屏推送迁移、真实 NAS HTTPS 与手机蜂窝网络验收仍需单独完成，不能以本地模拟测试替代。
具体准备与待实现边界见 [飞牛 NAS 指南](FNOS_HUB_GUIDE.md)。

## 事件同步参数与边界

- 本机 `thread/status/changed`、`thread/started`、关闭/归档事件更新内存投影；忽略工具输出和回复内容。
- 同一连接只为已经加载的会话执行一次无配置覆盖、`excludeTurns: true` 的 `thread/resume` 来订阅事件。
  不批量恢复历史会话。不支持该订阅方式的版本依靠低频校验；新会话的 Hook 会触发补充发现。
- 会话列表从每 2.5 秒改为每 60 秒校验，扫描次数约减少 96%；这是请求频率变化，不是性能跑分。
  事件到达时合并 100 毫秒内的补充发现请求；在途列表查询不会覆盖期间收到的新状态。
- 手机使用鉴权 `/changes?after=<opaque-revision>`，无变化最多等待 25 秒，有变化立即结束并读 `/snapshot`。
  即使没有事件，也在长轮询心跳返回后校验快照；旧 Relay 每 30 秒回退刷新。凭据仅放 Authorization 头。
- 手机网络故障使用 1–30 秒退避；回到前台重新取完整快照。手机证据超过 40 秒失效；App Server 证据超过
  75 秒失效，显式 WebSocket 断线立即失效。后台系统通知仍由已有 Hook/Web Push 路径负责。
- Queue 由对应会话事件唤醒，漏事件时最多 30 秒复查；发送前仍读取当前目标的元数据，Steer 保留活动回合前置条件。
- 变化流不包含 prompt、原始 thread ID 或对话；配对撤销会使已有等待请求也失去授权。

`App.tsx` 与 `server.mjs` 仍然偏大。本次先抽离多设备协调和状态投影，避免同时重写已有配对、权限、
通知和控制逻辑；后续可分别拆出单设备 hook 与鉴权路由。
